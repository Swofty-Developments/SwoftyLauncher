# T311 One resource larger than the free EGO_ERP_TEMP: wait, hang or fatal?

- Requested by: engine-re, 2026-11-20
- Status: draft
- Session: (filled by the lead when batched)

## Question
What does the ERP loader do when ONE resource's temp fragments (tags temp/tmp0/tmp1) are bigger than the largest free block of EGO_ERP_TEMP (500 MiB effective, win)?

## Hypothesis
`Game_EgoErpLoader_TryAllocTempSection` (0x143a69e90) retries only for a can-alloc status other than 0/0xc; status 0xc (largest free block too small) or a failed alloc goes to the no-return 0x1439182a0 (verifier V12105). Expected: a resource that cannot fit is a hard crash during the load, not a hang. Stock largest temp fragment: 7.0 MiB (Spa).

## Promotes
- `Game_EgoErpLoader_TryAllocTempSection` notes to L3 (retry path); core.md#track-erp-size-limits EGO_ERP_TEMP line.

## Build
- exe: 1.0.145 runtime; swofty_core with the Ne_ReportMemoryError hook.
- data: a test ERP with one GfxBufferRes of about 300 MiB temp (fits) and one of about 600 MiB (cannot fit).

## Trace config
1. Hook 0x143a69e90 return (rax) and the size/alignment of the EGO_ERP_LOADER_VERBOSE line; enable channel EGO_ERP_LOADER_VERBOSE if possible.
2. EGO_ERP_TEMP capacity/used/largest (heap vt+0x60/+0x68/+0x80) every 5 s during the load.

## User steps
1. Load the 300 MiB test track to the grid, quit. 2. Load the 600 MiB one; wait 3 minutes on the loading screen, then quit.

## Expected log lines
- repeated `tryAllocTempSection - waiting for temp memory` with the same size -> proves wait/retry (hang for the 600 MiB case).
- `Ne_ReportMemoryError ... EGO_ERP_TEMP` -> proves a fatal path instead.
Pass rule: 300 MiB loads, 600 MiB crashes in TryAllocTempSection (confirms the cap). Fail rule: 600 MiB loads or waits (then the temp path splits or retries).
