# T300 Which UI screens share one flattened layout tree, and how many slots does each tree hold with composed HUD screen records?

- Requested by: engine-re, 2026-11-19
- Status: draft
- Session: (filled by the lead when batched)

## Question
In a race with the HUD, the spectator screen and the replay screen opened once each, which root items (tree ids 0..14) does `Ui_LayoutTrees_WalkAll` walk, which screen's root is each, and how many slots does `Ui_LayoutTree_CountSlots` return per tree, with 0, 1 and 2 composed screen records (each on standings + replay + spectator)?

## Hypothesis
Static reading (ui_system.md#tree-limits): one registered root = one tree, at most 15 trees, the 65,536-slot limit is per tree. Every `<prefix>_host` eXRef and the stock standings `bottom_cap` hold a full copy of the grown cap, so a tree holding boards b costs k x cap with k = sum of (s_b + R_b). Expected: the HUD template screens (hud.ui with hud_dynamic_templates) are one root; hud_spectator_2 and replays_and_highlights are their own roots (then k per tree is 1 + R on the HUD tree and R on the others); if they share the HUD root, k = 1 + 3R.

## Trace config
Trace-only hooks (signatures still to be made with `sigcheck.py --make`):
- 0x14416771b (in `Ui_LayoutTree_Walk`, right after `call Ui_LayoutTree_CountSlots`): log eax (slot count), rsi (tree id, item+0x39), r14 (root node) and [r14+0x1a0] (its parent), rate-limited to changes per tree id.
- entry of 0x144166780 (`Ui_LayoutTrees_RemoveRoot`): log rdx (item) and byte [rdx+0x39], to see screens closing.
- optional: entry of `Ui_LayoutTree_Walk` 0x144167620, log r8 (item) and [r8+0x10] once per item pointer, to map item -> root.

## User steps
1. Start an offline Grand Prix race (no Time Trial), run A with no HUD screen records installed.
2. Drive one lap with the HUD, open the spectator screen once (pause menu or as configured), then open a replay (instant replay) for a few seconds, then quit to the menu.
3. Repeat with run B (one record) and run C (two records).

## Expected log lines
- `tree_count id=<n> slots=<count> root=<ptr>` per tree, each time a tree is re-flattened.
Pass rule: the slot difference of the tree that holds the standings board between run B and run A, and between C and A, fits k x cap with the k this test reports (count of host + stock instances in that tree). Fail rule: a different growth, which means instances are not node copies or more boards share the tree.
