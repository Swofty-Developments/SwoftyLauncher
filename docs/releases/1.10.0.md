# 1.10.0

Swofty Launcher for F1 25 1.10.0 replaces the Support tab with a Donate page, times Time Trial laps from their first flying lap, loads faster, keeps careers saved under earlier addon ids loading, runs on F1 25 1.0.145 in Steam and the EA app, keeps a plain copy of every career and puts back one the save lost, opens a list of your careers from Career with what each needs, adds std libraries for race control, standings, tyre damage, the pit lane and weather setup, and lets addon authors add bindings with one file.

## Launcher

- The **Support** tab is now **Donate**, with a heart icon.
- The page shows **Supporter** and **Supporter+** with their perks, and a one-time donation with **Claim previous donation**.
- The supporters wall is on the same page, Supporter+ first.
- The monthly goal bar is gone.
- The window title is **Swofty Launcher**.
- The in-game notice is titled **Swofty Launcher** with the launcher's version and lists what is new in it.
- The main menu no longer shows the braking point tile.
- A slow add-on helper that holds up the game's start is named in the known problems, and `loader.log` has a `[perf] slow addon init` line for each add-on whose init takes longer than a second.

## Early access

- An early access list on the Donate page shows the Supporter+ addon previews to everyone. F1 2011 is the first.
- A user who is not Supporter+ sees the Discord link locked, with **You must be Supporter+ to install**.

## Time Trial

- The first flying lap of a session gets its sector times.
- Ghost playback and the new personal best ghost work on the current Steam build of F1 25.
- A lap file carries the version of the launcher core that recorded it.
- A pause in the middle of a lap is accounted for in the lap's timing.
- The session starts with the Time Trial entrants capped at the game's vehicle table on the EA app's 1.0.145 as well.

## Loading

- The game's 3 second minimum for a track's loading screen, the story hub's loading screen and the change from one session to the next is skipped. A load that takes longer than 3 seconds takes as long as before. **Shorter loading waits** in SwoftyMod's settings turns it off. See [Loading waits](/using/swofty-mod#loading-waits).
- **Play** uses less disk space. The archives a build makes are linked into the game folder from the archive cache instead of copied, so each one is stored once, and the game files Play replaces are moved aside and renamed back on **Stop** instead of copied to a backup.
- **Play** reuses more of the previous build: an unchanged menu, car handling or ERS archive is linked from the archive cache instead of written again, a build whose hook outputs were rewritten with the same bytes is reused, and the changed parts of all of a build's archives are compressed together on several threads.
- The archive cache stays valid across launcher updates that do not change how builds are made, so the first **Play** after such an update reuses the archives.
- A saved build is rebuilt when your careers change.
- Building takes less time: stock files that are not packages are skipped, the HUD stock files are parsed once, a texture's slice count is read from its header, the stock database is hashed once, and resized resources are found with a vectorised search.
- Game database reads use a key index, so the track check, the career warnings, track activation and the stock id reads take less time.
- Team logo slices are encoded on worker threads and kept in a cache.
- Loading a career whose content renames characters takes less time: the core sets the career's strings in one pass.
- The launcher reads the Windows registry in process and keeps the install records for 30 seconds.
- `loader.log` has a step line for each boot and load phase, and the wrapper log has one line for each play phase from **Play** to the game's start and for the rollback.

## Careers and saves

- The launcher reads and writes F1 25's save files itself.
- Each profile keeps a plain copy of every career in its saves folder (`saves/<profile>/plain`). A new copy is taken when the game loads the save and each time it saves.
- A career missing from the save when the game loads it is put back from the newest plain copy. A career deleted in the game stays deleted.
- The save check finds the save file by its name instead of by its size.
- **Career** on the main menu opens a list of your careers, newest first, with **New Career** at the top. See [Resume Career](/using/career-saves#resume-career).
- A row shows the driver, the team in its colour, the content and mode, the season and race, and the status on the right: `Ready`, `Missing: <addon>`, `Made with another version of <addon>` or `Missing rows from <addon>`. Focus a row to see when it was last played and what it needs.
- The list shows the saves that have a driver and a team, including the careers of an addon's career mode while that addon is off. A save slot the game would not offer to continue is not listed.
- At the first **Play** after updating, the list reads the careers from the profile's save file.
- A ready row loads the career. A row that is not ready asks **Load Anyway** or **Back**. A `Missing rows from <addon>` row shows **Career can't load** and loads nothing, and so does a career of an addon's career mode when that addon is off or not installed.
- **New Career** opens the game's Career menu.
- `SWOFTY_RESUME_LIST=0` brings back the game's own Career menu and Resume Career screens.
- A career saved under the earlier ids of an addon's team, driver and car rows loads with its teams, drivers and cars. At **Play** the launcher maps such a career to the ids the rows have now once: in its plain copy, which the core puts in place when the game loads the save, or in the launcher's save file when there is no plain copy yet. See [Careers saved under earlier addon ids](/using/career-saves#careers-saved-under-earlier-addon-ids).
- A row loads only the career it shows. When the game's Career screen would open a career of another content or mode, the row does not load and `loader.log` says why.
- A test session or `swofty test shell` run without a saves fixture plays on the profile's launcher saves, as **Play** does. Earlier, the game played on Steam's own save in those runs.

## Game builds

- F1 25 1.0.145 works on Steam (1.0.145.2472) and in the EA app. The direct start, the title helper, the live car table and DRS, tyre damage, wheel and track wetness, the dropped scores rule, the Time Trial entrant cap, the player's name in Time Trial and the shader rule for the player's car run on both.
- Test runs on an EA app copy have their own sandbox, saves folder and save check.

## Seasons

- A box with more teams than its world has garages gets a world of its own, and a track is left out of a box whose own world has fewer garages than its teams.
- A box's track layer overrides that name a missing track layer are dropped.
- A pkg edit that sets a placement id outside 1 to 32 is refused, and so is a world extension past the game's 32 vehicle placements per kind.
- In a box with `race_tyre_change: false`, a race pit stop changes a punctured tyre on Steam 1.0.145 and keeps the other tyres. See [Sessions and weekends](/std/systems/sessions).
- A box's weather builds follow the weather setup chain rules. See [Weather setup](/reference/std/weather).

## Addon API

- New std libraries:
  - [Race control](/reference/std/race-control): events when the flag, the safety car, the red flag, a car's sector or a car's result status changes, and the current state.
  - [Standings](/reference/std/standings): the loaded career's drivers' championship in the game's order, with points and finishes per round (`career::standings()`, career ops version 8).
  - [Tyre damage](/reference/std/tyre-damage): each wheel's puncture state and deflation, and the `car.tyre.damage` event.
  - [Pit lane](/reference/std/pitlane): each car's garage and pit box.
  - [Weather setup](/reference/std/weather): the `session.weather.setup` event, the session's seed and a scripted forecast per dataset.
- A build hook's reply can list what it read (`build.reads`), and the core answers the hook with its kept reply while nothing it read changed. See [the build reply](/reference/addons/launcher-api/build-reply).
- The loader logs deprecated and dropped bindings when it loads and on their first resolve.

### Deprecated bindings

- `Ne_Property_SetS64IfChanged` is deprecated and leaves the addon API in the next release. It is a renamed binding: every caller sets a UIDBRef weak object reference through it and the compare is object identity, not a numeric S64 compare. Use `Ne_Property_SetUIDBRefIfChanged`.
- `Ne_Std_ThrowException` is deprecated and leaves the addon API in the next release. It is a renamed binding: it is `std::_Throw_bad_optional_access`, which only raises `std::bad_optional_access` and ends the process in a fast fail. Use `Ne_Std_ThrowBadOptionalAccess`.
- `Game_PitStopActionObserver_SetTransitionSequence` is deprecated and leaves the addon API in a later release. Its notes' exe claim is wrong: the only refuel strings are parts of the `EnsureFuelLoad` race objective names, and there is no fuelling string. It has no replacement.

## Contributing bindings

- A new binding is one JSON file under `re/bindings/<subsystem>/<Name>.json`. `binding.py new` writes it and proves it on your own game exe, `binding.py doctor` says whether the pull request would merge itself, and a pull request that adds only that file and passes every check merges itself. See [Adding a binding](/reference/addons/bindings).
- A renamed binding keeps its old name as a deprecated alias for a release.

## Under the hood

- The core's crate root is grouped into subsystem directories, and the store, the time trial and online clients and the launcher's pages are split into modules.
- The core's F1 25 modules are under `packages/core/src/games/f1_25`, behind re-exports, and a boundary test counts the shell's paths into them. The first **Play** after the update rebuilds the profile once.
- The native sources are formatted with clang-format 21, and CI checks the formatting.
- The binding tools run in time linear in the records, cache parsed records between runs, and check that no binding main exports stops exporting.
- The release carries the core's patch list, `patches.json`, by core version.
- Build-specific code in the core is gated on per-build proofs.
- CI and the offline tests run faster on hosted Windows.
